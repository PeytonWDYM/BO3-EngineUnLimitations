Capacity consumers

The server has 130,000 total slots. Slot zero is reserved, leaving 129,999 usable slots.
The client has 65,000 total slots and 64,999 usable slots.
Each slot uses 64 bytes. A 500,000-usable-slot server therefore needs 32,000,064 pool bytes.
A 1,000,000-usable-slot server needs 64,000,064 pool bytes.
These arithmetic sizes fit the reviewed allocator argument. They do not establish its heap budget or successful allocation.

The current-build instruction inventory finds nineteen server-capacity immediates in seventeen VM functions.
They cover allocation, free-chain initialization, lifecycle scans, state read/write, and notification or residual-stack keys.
The selected count must agree across these consumers for the lifetime of one pool.
Changing code while an old-sized pool exists can cause out-of-bounds access.
The inventory is a search result. Computed constants, indirect consumers, and mod assumptions still require review.

The separate hash table has 65,536 buckets with four-byte slot heads.
The reviewed collision chains use four-byte slot IDs. A bucket index is not a slot-ID width limit.
The reviewed special keys include capacity plus 131,072 and capacity plus 131,073.
Changing capacity also changes these keys. Existing objects cannot silently retain the old namespace.
No verified 17-bit or 18-bit slot ceiling was found. This is not a complete index-width proof.

Save layout and replay

The stock whole-pool reader and writer each process one record for every usable slot.
The VM section has a free-head field followed by a fixed number of records, without a capacity field there.
The parent save routines place section markers around their state data.
A changed record count changes the stream layout for a stock reader.
Keeping the writer count stock instead omits higher occupied slots and can preserve an out-of-range free head.

Twelve bounded native instruction replays passed against captured loop code.
They cover the reader and writer for both instances at the stock count and two hypothetical server counts.
The server performs 129,999, 500,000, or 1,000,000 per-slot calls, respectively.
The client remains at 64,999 calls in every case.
Each per-slot call uses an owned counter stub. The replay stops immediately after the native slot loop.
This proves loop behavior and the format mismatch. It is not a complete serializer, patch E2E, or game test.
The hypothetical count changes exist only in emulator memory.

A canonical ID remap can compact sparse IDs only when the live graph fits the stock capacity.
More than 129,999 distinct live slots cannot map one-to-one into the stock slot space.
A complete remap must also translate typed values, thread self IDs, child links, parent links, roots, and suspended stacks.
The state reader rebuilds hash entries. It also restores roots and entity-associated script references outside the slot loop.
The complete reference graph and a quiescent conversion point remain unverified.

Migration dependency

The current-build migration path calls the whole server-state writer through two native wrappers.
The outer function references EXE_MIGRATIONDROPPED and sends mstart after state serialization.
This establishes a migration consumer of the fixed-count server state. Earlier research left that relationship unresolved.

The migration buffer comes from a separate allocation family.
Its setup selects 2.5 MiB or 4.5 MiB for the server buffer, depending on the game mode.
The actual failing Zombies capture records 2.5 MiB for this buffer.
The migration writer passes this buffer and its capacity to the memory-file writer.
A larger VM allocation does not enlarge this buffer.

The mdata sender writes a block index and payload length as two-byte fields.
The receiver sign-extends both fields. It rejects negative indices and lengths outside 1 through 1,200.
Its offset calculation multiplies the block index by 1,200 and checks the end against the buffer capacity.
The acknowledgement returns the index through the same short writer.
The unchanged index field addresses 32,768 blocks, or 39,321,600 bytes.
A 32 MiB buffer fits this field. That arithmetic does not establish a sufficient save budget or working migration.
The migration header includes a four-byte state size in its 24-byte payload.
Sender acknowledgement tracking, deadlines, receiver completion, and compressed-size limits remain under review.

Prospective activation

All audited VM addresses refer to the decrypted mapped executable.
An on-disk patch cannot assume the packed executable contains those same bytes at the same offsets.
AAE frontend loading may provide an installation route for a prospective allocation hook.
That route still needs a verified server allocation or reset boundary and exact thread ownership.
A frontend screen alone does not prove an empty server VM. An earlier saved menu already contained allocated server slots.
The bounded direct-call inventory currently recovers a client allocation caller, but not the server's complete initialization route.
No verified claim that every map transition frees and reallocates this pool follows from that inventory.

Candidate direction

Use one fixed shared patch version and 500,000 usable server slots for the first candidate.
Keep the client capacity unchanged.
Bind every native edit to exact code bytes and the supported executable identity.
Install all count consumers before the corresponding server pool allocation, or reject activation.
Keep the chosen capacity stable until that pool is destroyed.

Matching patched peers can use an expanded state format, but they need explicit format admission.
Preserving campaign stock counts could avoid changing campaign save layout, after a verified mode and lifecycle audit.
Alternatively, a versioned reader must import a stock pool, rebuild its free chain, and translate capacity-derived keys safely.
Neither design is implemented or validated.
A 32 MiB migration buffer is a width-compatible candidate budget, not a verified replacement size.
Its allocation, sender, receiver, compression limits, deadlines, and failure handling must agree.

The release must not expose a functional 500k or 1m option from these findings alone.
Required next evidence includes native allocation/initialization/teardown behavior and complete matching-version state round trips.
Game validation must then cover full AAE, normal Zombies, host/join, migration, repeated map transitions, and removal.

AAE and acknowledgement follow-up

The captured full-AAE native module passes all six range hashes.
A bounded search found no literal server capacity, pool allocation size, allocator address, initializer address, or server pool-pointer address.
This includes the reviewed engine RVAs and their captured virtual addresses.
The client-capacity byte matches do not establish an AAE VM implementation.
Two matches occur inside call displacements. Inspected comparisons also handle character-conversion values.
Computed API addresses and indirect dispatch remain outside this literal search.

The server acknowledgement handler also sign-extends the returned block index.
It scans a fixed 32-entry sliding window, with twelve bytes per entry.
The next-block and total-byte fields use four-byte integers.
Thus the reviewed acknowledgement index does not require a larger window for a 32 MiB buffer.
This does not validate completion, retransmission, or timeout behavior at that size.

AAE initialization and actual pool backing (October 8 follow-up)

The captured AAE component registry contains 48 components, identified by their native RTTI names.
These include builtins, scheduler, hookmanager, asset_limits, and plugins.
All three reviewed component stages run synchronously from AAE's user DLL entry point.
This path does not establish an ordinary worker initialization point outside the loader lock.
The captured hook table contains 28 enabled entries. None directly targets the reviewed VM allocator or initializer.
AAE also uses other hook mechanisms. This table is not an exhaustive inventory of every AAE modification.
The builtins component changes native script-function registration; it does not provide a verified pool reset boundary.

The native pool allocator requests memory from the shared game/main linear arena with 128-byte alignment.
In the failure capture, that arena has a 2 GiB size field and a cursor of 1,546,514,320 bytes.
The remaining space under that captured cursor is 600,969,328 bytes.
The pool and hash-table pointers match consecutive arena allocations with exactly 8,320,000 bytes between them.
These observations identify the backing allocation. They do not guarantee every map's memory budget.
The reviewed allocation entry does not free an earlier pool before replacing its pointer.

The arena retains named allocation marks. The server pool lies within the $init region, before PerLocalClient.
LensFlareManager and UmbraLevel marks lie later in the arena.
The native named-mark release restores the selected top mark's cursor and can decommit its pages.
Releasing those later level marks does not reclaim the earlier server pool.
Therefore, a next-map pool reallocation cannot be assumed from a successful level teardown.
The remaining activation question is whether a supported mode/mod transition rebuilds $init after AAE loads.
A passive, process-bound before/after capture can distinguish a retained pool from a replaced one.
A working runtime patch still needs the exact initialization caller and thread contract.

Native allocation replay

The new private replay executes the captured allocation and initialization instructions, then consumes the entire pool through the captured object allocator.
Its owned heap stub records the actual requested size. Its owned memory-clear stub rejects writes outside an allocation.
An owned x64 caller records every returned slot ID. The native slot allocator itself is not stubbed.
Declared failure cases distinguish a larger clear against stock allocation from incomplete initialization of a larger allocation.
Both mismatched cases failed as expected.
The stock server, 500,000-slot candidate, and 1,000,000-slot candidate returned every ID in order and reached the native exhaustion branch.
The client still returned exactly 64,999 IDs with the hypothetical server count set to 1,000,001.
Every initialized slot and free-chain link was checked, including the sentinel and final zero link.
The resulting ordered ID streams have SHA-256 receipts in allocation-replay.json.
Expanded constants exist only in emulator memory. This does not test the actual game arena allocator, game activation, or live AAE behavior.

Legacy save import detail

The per-slot reader stores the saved 64-bit name/notification key and then rebuilds its hash-table entry.
A stock-save importer must translate the capacity-derived notification keys before this insertion.
Changing only the record count or adding a version tag would leave old notification keys in the expanded runtime.
The exact key categories and all equivalent references still need a complete typed translation audit.
No compatible expanded serializer or stock-save importer has been implemented.

Native serializer implementation checkpoint

The source now contains a server state adapter and its exact-build native bridge.
The adapter retains native per-slot codecs. The bridge copies the native whole-state tail fields.
These include nine roots, six pairs of script association fields, the native association codec,
the selected client roots, and the final native state field.
The client still uses its original whole-state reader and writer.

Expanded state begins with five DWORDs: magic, version, total capacity, client-root count, and free head.
The magic is 0x33564d50. The current format version is one.
A stock-sized runtime emits the stock prefix and record count, with its original client-root count.
The stock-sized writer refuses a changed client-root count before writing state.
The reader recognizes a legacy stock free head and reads exactly 129,999 records.
It retains slot IDs and translates the two verified category-one capacity-derived keys before hash insertion.
Other key categories retain their values. The importer checks the stock free chain and appends every extra free slot.
Matching expanded input must have the same capacity and client-root count.

The bridge exports a 48-byte, constant-initialized POD binding record.
Its C names and zero-initialized storage passed the owned executable export checks.
Its import context uses constant-initialized native TLS with no dynamic bridge initializer.
The debugger can publish binding data without executing a remote initialization function.
This does not establish stock hook activation or Steam process handoff.

Nine owned native fixture groups pass with /W4 /WX.
They cover legacy record count, extra free-chain reachability, key translation before insertion,
typed key preservation, expanded round trip, header refusal before state mutation,
stock output, original client calls, and the complete bridge tail.
The bridge tail replay retains root IDs above 130,000 and ten owned client-root structures.
The fixture uses owned fixed-size slot callbacks and owned image thunks.
It does not establish the game's ten-client allocation bound or complete variable-length codecs.
Its four-root legacy example is an owned case, not the failing game's configuration.

The separate captured-instruction replay executes the native per-slot writer, reader,
