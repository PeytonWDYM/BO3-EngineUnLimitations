VM startup gate: declared failures before implementation

Run only the fixed owned executable from its private build directory.
Never accept a game path or a process ID in the fixture runner.

1. Baseline: a decrypted owned allocator returns the original capacity.
2. The entry gate must stop before the first allocation and patch both count consumers.
3. Replacing encrypted bytes before execution must retain the hardware gate.
4. A TLS allocation before the executable entry must receive the new count.
5. A suspended worker must retain its thread handle, ID, priority, and resume count.
6. Concurrent workers must not execute a partly patched count pair.
7. A changed instruction must reject activation before either count changes.
8. A nonzero pool pointer must reject activation before either count changes.
9. An exit without reaching the gate must not count as activation.
10. A fault before the gate must reach the target exception path, without activation.
11. A repeated activation must reject the existing pool and changed instructions.
12. Remove the gate registers from every retained thread before readiness.
    Keep the debugger attached until exit if pending traps cannot be drained safely.
13. A client-first allocation must still apply both server-only edits before later server allocation.
14. A foreign debug-register assignment must reject activation without overwriting that assignment.
15. The readiness callback must run before any count consumer completes.
16. A nonowned single-step exception after readiness must reach the target handler.
17. A trace-flag single-step at the old gate address must reach the target handler.
18. The fixture must report whether the debugger remains present after readiness.
19. A nonzero hash pointer must reject activation while the pool pointer remains zero.

Use 500,000 and 1,000,000 usable slots in successful native allocation runs.
Record child status, allocation bytes, all visited IDs, and a deterministic ID receipt.
Negative runs retain read-only memory receipts from the stopped child before termination.
These cases prove Windows debugger chronology in an owned process only.
