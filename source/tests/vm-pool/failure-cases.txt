VM POOL EXPANSION: FAILURE CASES BEFORE IMPLEMENTATION

This is an investigation checklist. No engine patch exists.

1. A changed executable or mismatched capture invalidates the audit.
2. Allocated bytes and the initialized free chain disagree.
3. A lifecycle scan leaves higher slot IDs untouched.
4. A special notification key uses the old capacity and misses its counterpart.
5. A hash bucket or collision link truncates a higher slot ID.
6. A larger state writer emits more slot records than the stock reader consumes.
7. A larger state reader consumes later stock save fields as extra slot records.
8. A stock-sized writer omits allocated higher slots or emits a higher free head.
9. Loaded stock saves restore the old free chain and leave extra slots unreachable.
10. A host migration transfers expanded state to an unpatched peer.
11. A failed allocation, load, teardown, or removal leaves partially replaced state.
12. Full AAE replaces or assumes a stock-sized VM consumer.

The first bounded replay will execute captured loop instructions with owned call stubs.
It must preserve the client count and prove the actual fixed server iteration counts.
It must label call stubs and stop before unrelated game behavior.
This replay is evidence about save layout. It is not a patch E2E or game validation.

Allocation replay cases declared before extending the private harness:
- Raising initialization alone must be rejected when its clear exceeds the requested allocation.
- Raising allocation alone must fail full free-chain coverage for the requested capacity.
- Matching allocation and initialization must create exactly one sentinel and N reusable slots.
- The native allocator must return IDs above 65,535, 129,999, and 262,143 without truncation.
- Exhaustion must reach the native error branch before any out-of-range pool access.
- Client allocation and initialization must still produce exactly 64,999 usable slots.
The heap allocator and memory clear are owned emulator stubs. This does not test the game heap budget or activation timing.

Read-only lifecycle sampler cases, declared before implementation:
1. Reject a wrong executable hash, PE build, module, PID, or process creation tick.
2. Reject disabled profiles, missing code evidence, wrong mapped code, or changed reader source.
3. Reject globals outside the module and excessive mark counts before dependent reads.
4. Reject unreadable arena descriptors, name pointers, and unterminated bounded mark names.
5. Reject cursor/size disagreement, descending marks, and pool pointers outside the arena.
6. Accept fully uninitialized metadata without dereferencing null pointers.
7. Reject changing metadata or mark text across repeated reads. Do not claim atomic sampling.
8. Observe fixture-owned pool replacement, retained pool across time reset, and changed marks.
9. Exit cleanly when the owned process exits. Keep rejected-read evidence separate from samples.
10. Preserve target memory. Keep the pool and entity contents unreadable to prove metadata-only access.
11. Refuse an existing output path and output inside the repository, including directory junctions.
12. Retain source, profile, executable, command, output, and memory receipts outside the repository.
Rate is fixed at one sample per second. Server time and entity-pool pointers are observations, not a native world epoch.
